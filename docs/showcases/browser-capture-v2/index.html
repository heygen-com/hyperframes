A five-minute review path

Try the boundary, not just the happy path

  1. Open A1 through the local server. Run it. Expect two createImageBitmap calls and a canonical v2 result.
  2. Run B7. It should refuse the second resource and keep the decoder meter at zero. Any call is a batch atomicity failure.
  3. Run E9. Wait for the deadline. It should finish with resource.materialization-aborted, never spin forever.
The honest boundary

What this packet does not prove

The extension handoff is not in these clips

This bench exercises the shipped core contract directly in Chrome. It does not claim the extension toolbar, target-page clipboard warning, or Studio paste flow is complete. The creator-mode clipboard warning remains the next U2A gate.

One browser decoder is represented

The real image capability here is Chromium 152 createImageBitmap. Other browser engines may reject different corrupt payloads and need their own witness run.

What was actually verified

  • The current packages/core build completed.
  • Five real Chrome gestures persisted five matching JSON witnesses.
  • Every recording was inspected as a filmstrip.
  • Five H.264 MP4s decode at 1280 by 900, 30 fps, with no audio stream.

Why the meter matters

A refusal code alone can hide wasted work. The materializer count proves both safety and ordering: cheap batch checks finish before expensive browser capabilities begin.

Recorded from a 1500 by 940 headless Chrome viewport against the built @hyperframes/core/web-capture package. The visible cursor is drawn by the capture harness because browser screencasts do not include the operating system cursor.
